SAAMOS ✦

An offline assistive system exploring how voice interaction, computer vision, and directional audio can make everyday information more accessible to blind and low-vision users.

My role Team lead · Audio development · Integration & testing
Platform TI SK-AM62 · Embedded Linux · Python
Design goal Offline, voice-first, accessible interaction

It started with a person, not a feature ♡

What motivates me most about engineering is the opportunity to make someone's life easier. With SAAMOS, our team wanted to explore a practical accessibility question: how could someone ask about nearby objects and receive useful spoken feedback without depending on a network connection?

The project focuses on voice commands, local processing, and audio responses as building blocks for an assistive experience.

It is a developing prototype, not a tested mobility aid or a replacement for a cane, guide dog, or other accessibility tools.

How the system works

SAAMOS connects audio input, a command controller, object-detection results, and synthesized responses. The pipeline is designed for offline operation on embedded Linux hardware.

01 · Speak a request Microphone input and local speech-to-text, using Vosk in development.
↓
02 · Interpret the request The controller decides whether to describe the scene, locate an object, or stop.
↓
03 · Get visual information The vision subsystem supplies object labels and relative positions. Mock results are used in integration tests.
↓
04 · Speak the result Text-to-speech and directional cues communicate the response through audio.
Why offline? Reducing reliance on connectivity is a design choice intended to make basic assistance available in more settings. Real-world reliability and accessibility still need evaluation.

A prototype interaction

Here's an example from the integrated controller tests. It shows how a request can turn into a concise, directional response.

USER > What do you see?
SAAMOS > Bottle left, cup right, laptop center.
USER > Where's my guitar?
SAAMOS > Not found.
USER > Stop.

What we tested

Testing individual components before tying them together was important because the microphone, vision model, controller, and hardware did not always develop at the same pace.

  • Built automated Python tests for text-to-speech, microphone handling, and speech-to-text.
  • Used mocked system calls and mock vision output to validate command flows before relying on every hardware component.
  • Tested scene-description, missing-object, and stop-command responses through the integrated controller.
  • Ran an integrated test suite during development, with 62 tests reported passing in a later local run.
What these results do—and don't—show: Automated tests support software integration confidence. They do not establish real-world obstacle-detection accuracy, safety, or usability for blind and low-vision users.

Engineering challenges & lessons

Getting multiple subsystems to agree

A working speech module alone isn't enough: the controller must interpret commands, the vision results need to be usable, and the response has to reach the user clearly. Mock interfaces let us keep progressing while other parts were still under development.

Building for an embedded target

Developing on macOS while preparing the TI SK-AM62 board required careful attention to device-specific dependencies, offline execution, and what could actually be tested on each platform.

Leading with the user in mind

The biggest lesson is that technical functionality and genuine accessibility are different milestones. Real user feedback, reliability under changing conditions, and appropriate safeguards matter as much as passing code tests.

What's next?

  • Complete hardware-level testing with camera, microphone, and audio output connected to the board.
  • Record a clear end-to-end demonstration with real inputs and explicitly show any limitations.
  • Evaluate whether audio descriptions are helpful, timely, and understandable with input from intended users.
  • Document system architecture, latency, and failure cases as testing matures.

I'm especially excited to keep learning how accessible design can guide better engineering decisions.
